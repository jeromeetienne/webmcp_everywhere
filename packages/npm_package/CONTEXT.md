# Directory Context: `/packages/npm_package`

## Purpose
What npmjs carries and what a user installs: the extension, the bundled native messaging host, the launcher Chrome starts, and the command `npx webmcp_everywhere` runs. This folder is the package, so what npm publishes can be read in a diff rather than assembled by a program.

## Key Exports & Entry Points
- `package.json`: the published manifest, committed. Its `files` list is what travels; `ReleaseLayout.PUBLISHED_ENTRIES` names the same entries for the copy and the archive.
- `README.md`: what a user reads, written for somebody who will never open this repository.
- `webmcp_native_host.sh`: the launcher Chrome starts, which finds a Node.js and runs the bundle beside it.
- `native_messaging_template/`: the host manifest template the installer fills in — see its own CONTEXT.md.
- `src/`: the installer, the command, and what they need. Bundled by esbuild, never published.
- Commands: `npm run package:release` builds the four things this folder cannot commit; `npm run pack:npm` packs the result.

## Rules
- The manifest, the notes, the licence, the launcher and the template are committed. Only `chrome_extension/`, `webmcp_native_host.mjs`, `install_the_native_messaging_host.mjs` and `webmcp_everywhere.mjs` are built, they are the `ReleaseLayout.GENERATED_ENTRIES`, and `.gitignore` names those four. `package_release.ts` clears exactly those rather than emptying this folder.
- **Nothing under `src/` names a path that only exists in a working copy.** Every path the installation reads is passed in by its caller: a release names files beside itself, and a working copy names `tools/working_copy_layout.ts`. A default of its own would be a path that is right here and missing for every user, and no check here would catch it.
- `src/` is bundled and never published, which is why `files` leaves it out and why `tests/repository_layout/source_boundary.test.ts` does not hold this package to the rule that a relative import may not leave it. No import uses that room: `HostStateFiles` and the endpoint shapes are reached as `@webmcp_everywhere/native_messaging_host`, which is what [issue #19](https://github.com/jeromeetienne/webmcp_everywhere/issues/19) made possible. Publishing `src/` would fail anyway: Node.js refuses to strip types under `node_modules`.
- This is the one package that is not `"private": true`, because [issue #12](https://github.com/jeromeetienne/webmcp_everywhere/issues/12) put it on npmjs. `tests/repository_layout/workspace_packages.test.ts` refuses a second publishable package.
- The version here, the one in `contribs/chrome_extension/manifest.json` and the release tag say the same thing, which `tools/version_agreement.ts` checks and `package_release.ts` refuses to package without.
- A file name inside a packaged release is spelled once, in `src/release_layout.ts`. Four programs need those names, and the fourth is where a stale one hides.
- Every way of installing something has a way back, as easy to find: `npx webmcp_everywhere uninstall` removes the host manifest and this folder's copy, and leaves the token and the loaded adapters alone.

## Background
- The package on npmjs, and why an npx run must not leave Chrome pointing at a folder npm will empty, is [issue #12](https://github.com/jeromeetienne/webmcp_everywhere/issues/12).
- It became a workspace package in milestone 3 of [issue #11](https://github.com/jeromeetienne/webmcp_everywhere/issues/11). Before that the whole folder was generated by `tools/package_release.ts`, which held the launcher as 51 lines of shell inside a TypeScript template literal and the notes as 60 lines of Markdown inside another.
- Splitting `ExtensionIdentifier` out of `tools/generate_extension_key.ts` came from the same milestone, and it took the key-pair generation — which writes into `contribs/chrome_extension/manifest.json` and could never work for a user — out of both published bundles.
